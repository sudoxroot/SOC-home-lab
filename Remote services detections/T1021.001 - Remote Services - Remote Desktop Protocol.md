
## 1. Overview

This lab documents a controlled remote authentication attempt from a Kali Linux machine against a Windows system.  
The goal was to generate authentication telemetry, forward the Windows Security logs through Winlogbeat into the ELK stack, and investigate the resulting failed logon event in Kibana.  
The lab environment included:

- Kali Linux: attacker
    
- Windows: victim
    
- Sysmon: endpoint telemetry
    
- Winlogbeat: Windows log collection
    
- Logstash: log processing
    
- Elasticsearch: log storage
    
- Kibana: investigation and visualization
    

All testing was performed in an isolated home lab.

1. Confirm that the Windows RDP service was reachable.

## 7. Logon Type Analysis

The event recorded:

```
Logon Type: 3
```

Logon Type 3 represents a network logon.  
This matters because the event should not automatically be described as an RDP logon simply because the connection was made to TCP port 3389. RDP activity is commonly associated with Logon Type 10, but that was not the value recorded in this event.  
The authentication details were:

```
Authentication Package: NTLM
Logon Process: NtLmSsp
```

The source address was:

```
192.168.0.107
```

This address belonged to the Kali machine.  
Based on the fields that were actually captured, the most accurate description is:

> A remote network authentication attempt from the Kali machine failed against the local Windows account `victim`.  
> The RDP service was confirmed to be reachable on TCP/3389, but the 4625 event itself should be treated as a network authentication failure. The event does not, by itself, prove that a successful or failed RDP logon was recorded as Logon Type 10.

The event contained the following status values:

## 9. ELK Investigation

The Windows Security event was collected and forwarded into the ELK stack.  
I investigated the event in Kibana using:

```
event.code: "4625"
```

To focus on failed authentication attempts from the Kali machine, I used:

```
event.code: "4625" AND source.ip: "192.168.0.107"
```

If the source address was stored in the Winlogbeat event structure rather than the ECS `source.ip` field, the following query could be used:

```
event.code: "4625" AND winlog.event_data.IpAddress: "192.168.0.107"
```

## 11. SOC Detection Logic

A single failed authentication does not necessarily indicate malicious activity.  
Windows can generate Event ID 4625 for several legitimate reasons, including:

- Incorrect passwords
    
- Expired credentials
    
- Misconfigured services
    
- Old saved credentials
    
- User mistakes
    
- Network authentication problems
    

For that reason, a useful SOC detection should focus on repeated activity rather than one isolated event.  
A simple detection pattern would be:

```
Multiple Event ID 4625 events
        +
Same source IP
        +
Short time window
        +
Same or multiple target accounts
        ↓
Suspicious authentication activity
```

For this lab, the relevant values were:

```
Source IP: 192.168.0.107
Target Account: victim
Event ID: 4625
Logon Type: 3
Authentication: NTLM
```

Repeated failures from the same source would make the activity more suspicious and could indicate password guessing or another credential attack.

## 15. Final Detection

A basic Kibana query for this lab is:

```
event.code: "4625" AND source.ip: "192.168.0.107"
```

A broader detection can search for all failed logon events:

```
event.code: "4625"
```

The results can then be grouped or aggregated by:

```
source.ip
TargetUserName
LogonType
AuthenticationPackageName
```

Repeated failures from the same internal or external source should be reviewed for possible password guessing, credential misuse, or service misconfiguration.

## Conclusion

This lab generated and investigated a failed Windows authentication event originating from Kali Linux.  
The captured telemetry showed:

```
4625
Logon Type 3
NTLM
Source: 192.168.0.107
Target: victim
Workstation: kali
```

The event was collected through the Windows logging pipeline, forwarded into the ELK stack, and investigated in Kibana.  
The exercise showed how a SOC analyst can move from a raw endpoint event to a useful security finding by reviewing the source IP, target account, authentication method, logon type, and pattern of repeated failures.
