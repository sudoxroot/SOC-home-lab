
# Password Spraying Detection Using Windows Event Logs and ELK

## Overview

In this lab I simulated a password spraying attack from Kali Linux against a Windows machine and monitored the authentication activity through Windows Security logs and ELK.  
The main objective was to understand how password spraying appears from a defender's perspective and how multiple failed authentication attempts can be correlated to identify the source of the activity.

MITRE ATT&CK technique:  
T1110.003 Password Spraying  
Tactic: Credential Access

## Lab Environment

Attacker: Kali Linux  
Attacker IP: 192.168.0.107  
Victim: Windows 10  
Victim IP: 192.168.0.104  
SIEM: ELK  
ELK IP: 192.168.0.108  
Windows logging: Windows Security Logs and Sysmon  
Log forwarding: Winlogbeat → Logstash → Elasticsearch → Kibana

## Preparing the Lab

I created several dedicated test accounts on the Windows machine. These accounts were created only for the lab and were not connected to any real user accounts.  
Example accounts:  
spray01  
spray02  
spray03  
spray04  
spray05

The idea behind the attack was to test the same password against multiple accounts instead of trying many passwords against a single account.  
For example:  
spray01 → WrongPassword123!  
spray02 → WrongPassword123!  
spray03 → WrongPassword123!  
spray04 → WrongPassword123!  
spray05 → WrongPassword123!

This is the important difference between password spraying and traditional brute force. In a brute force attack, an attacker generally tries many passwords against one account. In password spraying, the attacker uses one or a small number of common passwords against multiple accounts.

## Windows Audit Configuration

Before starting the attack, I made sure Windows was auditing failed logons.  
I checked the Logon audit policy using:

```powershell
auditpol /get /subcategory:"Logon"
```

Failure auditing was enabled so that unsuccessful authentication attempts would generate Windows Security Event ID 4625.

I also verified that the Windows Server service was running and that SMB was available because the authentication test was performed through SMB.

## SMB Connectivity Problem

My first attempt did not generate any authentication events.  
The reason was not ELK. The Windows SMB port was being filtered.  
I checked the port from Kali using:

```bash
nmap -Pn -p445 192.168.0.104
```

The result showed:

```text
445/tcp filtered microsoft-ds
```

This meant that the authentication request was not reaching the Windows SMB service.  
I checked the Windows SMB service and firewall configuration and enabled the required File and Printer Sharing firewall rules for the isolated lab network.  
After fixing the connectivity issue, port 445 became reachable from Kali.

## Password Spraying Simulation

I used NetExec from Kali to perform the authentication tests against the Windows machine.  
A single test was performed first to confirm that Windows was generating the expected security event:

```bash
nxc smb 192.168.0.104 -u spray01 -p 'DefinitelyWrongPassword123!'
```

After confirming that the authentication request was reaching Windows, I tested the same password against multiple dedicated lab accounts.

The important pattern was:

```text
192.168.0.107 → spray01 → failed authentication
192.168.0.107 → spray02 → failed authentication
192.168.0.107 → spray03 → failed authentication
192.168.0.107 → spray04 → failed authentication
192.168.0.107 → spray05 → failed authentication
```

## Windows Detection

The failed authentication attempts generated Windows Security Event ID 4625.  
I checked the events through:  
Event Viewer → Windows Logs → Security

The most useful fields were:  
Event ID  
Target username  
Source IP address  
Logon Type  
Status  
SubStatus  
Authentication Package

The source IP was the Kali machine:  
192.168.0.107

The target machine was:  
192.168.0.104

The authentication attempts used Logon Type 3, which represents a network logon. This made sense because the test was performed through SMB.

## ELK Detection

After confirming the events were being generated locally on Windows, I checked whether Winlogbeat was forwarding the Security events through the ELK pipeline.  
The logging path was:  
Windows Security Log  
→ Winlogbeat  
→ Logstash  
→ Elasticsearch  
→ Kibana

In Kibana I searched for:

```text
event.code: 4625
```

I then narrowed the search to the Kali source IP:

```text
event.code: 4625 AND source.ip: "192.168.0.107"
```

This allowed me to see the authentication failures generated by the attack.

## Detection Logic

A single Event ID 4625 does not necessarily mean password spraying.  
A failed authentication can happen for many normal reasons, such as a user entering an incorrect password.  
The more useful detection comes from correlating several failed authentication events.

The detection logic used in this lab was:

```text
Multiple 4625 events
Same source IP
Multiple different usernames
Short time window
Network logon activity
```

For example:

```text
Source IP: 192.168.0.107
Failed attempts: 5
Distinct usernames: 5
Time window: 10 minutes
Logon Type: 3
```

This is much more suspicious than five failed attempts against the same account.

## Brute Force vs Password Spraying

Traditional brute force:

```text
192.168.0.107 → spray01 → password1
192.168.0.107 → spray01 → password2
192.168.0.107 → spray01 → password3
192.168.0.107 → spray01 → password4
```

Password spraying:

```text
192.168.0.107 → spray01 → same password
192.168.0.107 → spray02 → same password
192.168.0.107 → spray03 → same password
192.168.0.107 → spray04 → same password
```

The second pattern is what I focused on detecting in this lab.

## Investigation Process

When investigating the alert, I would start with the source IP and determine which accounts were targeted.  
Then I would look at the timestamps to determine whether the failures occurred within a short period.  
After that I would inspect the Logon Type, authentication package, status and substatus values.  
The next step would be checking whether the same source generated any successful authentication events.

A particularly interesting situation would be:

```text
4625 → spray01
4625 → spray02
4625 → spray03
4624 → spray03
```

A successful 4624 after multiple 4625 failures could indicate that the attacker eventually found a valid credential.

## Detection Summary

The main detection indicators from this lab were:  
Windows Event ID 4625  
Multiple failed network logons  
Same source IP  
Multiple targeted usernames  
Short time period  
Potential 4624 after the failed attempts

The most important lesson from this experiment was that detecting password spraying should not depend on a single failed login event.  
The useful signal comes from looking at the authentication activity as a pattern.

## Conclusion

This lab helped me understand the complete path from an authentication attack to SIEM detection.  
The attack originated from Kali, the authentication failures were recorded by Windows, Winlogbeat forwarded the events to Logstash, and the events were ultimately searchable in Kibana.  
The biggest troubleshooting issue was SMB connectivity. Initially port 445 was filtered, so the authentication request never reached Windows and no 4625 event was generated.  
After fixing SMB connectivity, the authentication activity could be monitored through Windows Security logs and correlated in ELK.  
The final detection was based on the combination of failed authentication events, source IP, targeted usernames and timing rather than treating every 4625 event as an attack.
